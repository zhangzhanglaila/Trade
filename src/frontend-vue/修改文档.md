## 三、后端接口需求

### 3.1 新增接口清单

#### 1. 创建本体（支持文件上传）

```http
POST /api/ontology/create-with-file
Content-Type: multipart/form-data
```

**请求参数**：
| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| ontologyName | string | 是 | 本体名称 |
| creatorName | string | 是 | 创建人 |
| version | string | 是 | 版本号 |
| namespaceUri | string | 是 | 命名空间URI |
| fileFormat | string | 是 | 文件格式(OWL/RDF/Turtle/N-Triples) |
| file | File | 否 | 本体文件 |

**响应**：
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "ontologyId": 123,
    "ontologyName": "xxx",
    "version": "v1.0"
  }
}
```

**说明**：
- 如果上传了文件，后端需要解析文件内容创建本体
- 如果没有上传文件，创建空本体（仅元数据）

---

#### 2. 检查本体名称是否存在

```http
GET /api/ontology/check-name/{ontologyName}
```

**响应**：
```json
{
  "code": 200,
  "data": {
    "exists": true,
    "namedGraphs": ["http://example.com/graph/ontology1"]
  }
}
```

**说明**：
- 用于判断是首次入库还是更新版本
- `namedGraphs`：图数据库中对应的图名称列表

---

#### 3. 获取本体版本历史

```http
GET /api/ontology/{ontologyName}/versions
```

**响应**：
```json
{
  "code": 200,
  "data": [
    {
      "ontologyId": 123,
      "version": "v1.0",
      "createTime": "2024-01-15 10:30:00",
      "status": 1
    },
    {
      "ontologyId": 122,
      "version": "v0.9",
      "createTime": "2024-01-10 14:20:00",
      "status": 0
    }
  ]
}
```

**说明**：
- 按时间倒序排列，最新的排在最前面
- `status`: 1-当前版本, 0-历史版本

---

#### 4. 本体入库（新增/更新版本）

```http
POST /api/ontology/import-to-house
Content-Type: multipart/form-data
```

**请求参数**：
| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| sourceOntologyId | long | 是 | 源本体ID（业务库中的ID） |
| newVersion | string | 是 | 新版本号 |

**业务逻辑**：
1. 检查 `ontologyName` 是否已存在于图数据库
2. 如果不存在：创建新图，将本体数据导入图数据库，标记为 v1.0
3. 如果存在：在现有图基础上更新数据，创建新版本记录
4. 将本体数据从业务库同步到图数据库

**响应**：
```json
{
  "code": 200,
  "message": "入库成功",
  "data": {
    "ontologyId": 123,
    "version": "v1.1",
    "namedGraph": "http://example.com/graph/ontology1"
  }
}
```

---

#### 5. 版本回滚

```http
POST /api/ontology/rollback
Content-Type: application/json
```

**请求体**：
```json
{
  "sourceOntologyId": 123,
  "newVersion": "v1.0"
}
```

**业务逻辑**：
1. 根据 `sourceOntologyId` 和 `newVersion` 找到对应版本的数据
2. 将图数据库中的数据回滚到该版本状态
3. 将该版本标记为当前版本

**响应**：
```json
{
  "code": 200,
  "message": "回滚成功"
}
```

---

#### 6. 导出本体文件

```http
GET /api/ontology/{ontologyId}/export?format=OWL
```

**请求参数**：
| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| ontologyId | long | 是 | 本体ID（路径参数） |
| format | string | 是 | 导出格式(OWL/RDF/Turtle/N-Triples) |

**响应**：
- Content-Type: `application/octet-stream`
- 返回文件流，前端下载

**文件后缀对应关系**：
| format | 后缀 |
|--------|------|
| OWL | .owl |
| RDF | .rdf |
| Turtle | .ttl |
| N-Triples | .nt |

## 四、数据库设计建议

### 4.1 本体版本表（ontology_version）

```sql
CREATE TABLE ontology_version (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    ontology_id BIGINT NOT NULL COMMENT '本体ID（业务库ID）',
    ontology_name VARCHAR(255) NOT NULL COMMENT '本体名称',
    version VARCHAR(50) NOT NULL COMMENT '版本号',
    named_graph VARCHAR(500) COMMENT '图数据库中的图名称',
    status TINYINT DEFAULT 0 COMMENT '状态：0-历史版本, 1-当前版本',
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_ontology_name (ontology_name),
    INDEX idx_version (version)
);
```

### 4.2 图数据库设计

- 每个本体对应图数据库中的一个 Named Graph
- Named Graph 命名规范：`http://{host}/graph/{ontologyName}` 或 `urn:graph:{ontologyName}`
- 版本信息存储在业务库，图数据库只存储当前状态数据

## 五、接口调用流程

### 5.1 入库流程

```
1. 点击"入库"按钮
   ↓
2. 调用 checkOntologyName(ontologyName)
   ↓
3. 判断 exists 字段
   ├── false（不存在）→ 显示"首次入库"界面
   │                    输入版本号 → 调用 importToHouse()
   │
   └── true（存在）→ 调用 getOntologyVersion() 获取历史版本
                      显示"更新版本"界面
                      ├── 输入新版本号 → 调用 importToHouse()（更新）
                      └── 点击回滚 → 调用 rollbackOntology()
```

### 5.2 新增本体流程

```
1. 点击"新增本体"
   ↓
2. 填写表单，选择文件（可选）
   ↓
3. 点击保存
   ├── 有文件 → 调用 createOntologyWithFile()（multipart/form-data）
   └── 无文件 → 调用原有 addOntology()（application/json）
```

## 六、注意事项

### 6.1 前端注意事项

1. **文件大小限制**：建议限制单个文件不超过 50MB
2. **版本号格式**：建议前端做格式校验（如 v1.0.0）
3. **并发控制**：入库操作较慢，需要 loading 状态
4. **错误处理**：入库失败需要明确提示原因

### 6.2 后端注意事项

1. **事务控制**：入库操作涉及业务库和图数据库，需要保证数据一致性
2. **版本冲突**：同一本体并发入库需要加锁或乐观锁控制
3. **文件解析**：OWL/RDF 文件解析可能耗时较长，建议异步处理
4. **存储空间**：版本历史会占用额外存储，需要定期清理旧版本

### 6.3 接口兼容性

- 现有接口保持不变，新增接口独立
- 建议版本号：`/api/v2/ontology/xxx` 或保持 `/api/ontology/xxx`
- 返回格式保持统一：`{ code, message, data }`
