# 中哈贸易系统 · 服务器部署指南

> **读者对象**：第一次接手该项目的工程师，或在服务器上代为执行部署的 AI Agent。
> **目标**：从一台干净的服务器开始，把系统跑起来，并让前端看到**真实数据**（而非随机生成的测试数据）。
> **项目根**：本文所有相对路径都以项目根为基准（例如 `/opt/trade`）。

## 3. 环境要求

| 依赖 | 版本 | 说明 |
|---|---|---|
| JDK | **17** | `backend-main` 与 `backend-training` 均为 Java 17。`src/pjcait/collector` 需要 JDK 21，仅在其单独部署时需要 |
| Maven | 3.8+ | 构建后端。**需能访问 Maven 中央仓库**，否则先在联网机器 `mvn dependency:go-offline` 后拷贝 `~/.m2/repository` |

## 4. 部署步骤

> **顺序**：4.0 打包上传 → 4.2 初始化 MySQL → 4.3 图谱入库 → 4.4 构建 → 4.5 启动 → 4.6 Nginx。
> 4.2 必须在 4.4/4.5 之前（否则后端启动即报表不存在）；4.3 与 4.4 无先后关系，但 **4.3 导入时请先停后端**（TDB 单写者）。

### 4.0 从开发机打包与上传

**不要直接把整个项目目录拷到服务器**。21.67 GB 里有几块是「传过去反而会坏事」的：

| 内容 | 体积 | 为什么不能直传 |
|---|---|---|
| `**/node_modules` | 1.08 GB / 147,375 文件 | 在 Windows 上安装的依赖，含 **10 个 `.node` 原生二进制**。Linux 加载会报 `invalid ELF header` / `Cannot find module ...binding.node`。**服务器上 `npm ci` 重装** |
| `**/target`、`**/dist` | 约 1 MB+ | Windows 上编译的 `.class` / jar 在 Linux 不可用；服务器上重新构建 |
| `models/`（需 `--with-models`） | 18.07 GB | 只有要另起大模型推理服务时才需要，默认排除 |
| `.git`、`logs`、`archive`、`.idea` | 约 12 MB | 无运行价值；`archive` 纯属归档 |

打包脚本已备好（开发机执行，只需 Python 3，无第三方依赖）：

```bash
# ① 先预览会打包什么、排除什么
python deploy/package-for-server.py --dry-run

# ② 正式打包 → 输出到 <项目根上级>/_upload/trade-server-<日期>.tar.gz
python deploy/package-for-server.py

# ③ 若服务器还要跑问答大模型（+17.8 GB）
python deploy/package-for-server.py --with-models
```

本机实测结果：**上传包 2.51 GB / 18,622 文件**，压缩后约 700 MB。被排除的：`models` 18.07 GB、`node_modules` 1.08 GB、`.git` 6.5 MB、`logs` 5.6 MB、`target` 1 MB、`archive` 0.3 MB、`.idea` 0.24 MB、`*.log`/`*.bak` 0.5 MB。

脚本以 **PAX 格式 tar.gz** 打包（正确处理中文与全角括号文件名），归档内顶层目录是 `trade/`，解包即为 `/opt/trade/`。

```bash
# 开发机 → 服务器
scp _upload/trade-server-2026-09-27.tar.gz user@server:/tmp/

# 服务器上解包
sudo mkdir -p /opt && cd /opt
sudo tar -xzf /tmp/trade-server-2026-09-27.tar.gz
sudo chown -R $USER:$USER /opt/trade
cd /opt/trade && chmod +x deploy/*.sh
```

> ⚠️ **传输方式**：用 `scp` / `rsync` / 上文 `tar` 即可（二进制传输）。**不要用图形 FTP 客户端的"文本/ASCII 模式"**——那会把 `deploy/*.sh` 的 LF 改写成 CRLF，Linux 执行时报 `bash^M: bad interpreter`。仓库里的 `.sh` 已经是 LF，无需 `dos2unix`。
>
> ⚠️ **中文文件名与 locale**：项目里存在 `data/01_原始_海关进出口明细/`、`deliverables/本体与映射规则/trade（protege建模导出）.rdf`（含**全角括号**）等路径。请确认服务器 locale 为 UTF-8（`locale` 输出应含 `C.UTF-8` 或 `zh_CN.UTF-8`）；若是 `C` / `POSIX`，中文目录会出现乱码或"文件找不到"。临时解决：`export LANG=C.UTF-8 LC_ALL=C.UTF-8`。
>
> 💡 **只想先跑起来看效果**？那就用上面的最小上传包（不加 `--with-models`），跳过 §8.2，问答功能会退化为关键词路由，其余功能全部可用。

### 4.1 放置代码

若已按 §4.0 用 `tar` 解包到 `/opt/trade`，这一步已完成。其它方式：

```bash
sudo mkdir -p /opt/trade
# rsync（推荐，可比对增量）
rsync -av --exclude node_modules --exclude target --exclude .git ./ user@server:/opt/trade/
# 或 git clone（各子目录是独立仓库，需逐个 clone）
```

解包/同步后确认目录结构与本指南 §2 一致，然后：

```bash
cd /opt/trade
ls -d src data deliverables docs deploy tools    # 应全部存在
```

**无需修改任何绝对路径**——见 §5 说明。

### 4.2 初始化 MySQL（必需，否则后端启动即报错）

```bash
pip3 install pymysql
python3 deploy/init_mysql.py --password '<你的MySQL root密码>'
```

脚本会依次：
1. 建库 `foreign_trade_qa_db` 与全部 8 张表（含缺失已久的 7 张业务表 DDL）；
2. 导入 `data/01_原始_海关进出口明细/**` 约 234 万行 → `trade_records`；
3. 导入 `data/04_采集_新闻语料/*.csv` → `news_articles`；
4. **由真实数据聚合**生成 `country_monthly_trade` / `trade_method_stats` / `corpus_entries` / `comprehensive_data`（不再使用 `Math.random()` 假数据）。

常用变体：

```bash
# 只想快速起服务，不想等 234 万行写完（统计表仍会按真实数据聚合）
python3 deploy/init_mysql.py --password xxx --skip-trade-records

# 只建表
python3 deploy/init_mysql.py --password xxx --schema-only

# 只重建语料和汇总
python3 deploy/init_mysql.py --password xxx --news-only
```

> ⚠️ 若 MySQL 账号不是 root，或端口不是 3306，用 `--user --host --port` 指定。
> ⚠️ 连接信息同时要写进 `src/backend-main/src/main/resources/application.yaml` 的 `spring.datasource`。

### 4.3 导入知识图谱到 Jena TDB（**决定图谱页有没有数据可读**）

后端用的是嵌入式 Jena **TDB1**（`org.apache.jena.tdb.TDBFactory`），图库是文件型目录，**首次部署必须显式导入**，否则图库里没有任何数据。

> ⚠️ **本步只决定「图库里有没有数据」，不决定「图谱页能不能画出来」。**
> 历史版本在此之后图谱页**仍然是空白**，还需要 §11 的三处修复（命名图 URI、
> 类型断言、前端假数据兜底）。若你手上的代码已包含这些修复则无需额外操作。
> 早期文档在此处写「决定图谱页能否显示数据」并称"导入即可用"，**该说法不准确**。

```bash
cd src/backend-main
mvn test -Dgraph.import=true -Dtest=RdfBulkImportTest
```

控制台会输出进度与导入前后的三元组数。**实测（2026-09-28，含 §10.9 修复后的数据）：
276 个文件、导入后 3,562,916 条三元组、失败 0 个**。
（早期文档写的"≈ 226 万条"是未修复数据时的口径。）

可调参数：

```bash
mvn test -Dgraph.import=true -Dtest=RdfBulkImportTest \
  -Dgraph.store=/opt/trade/runtime/ontology-graph-store \
  -Dgraph.dir=/opt/trade/data/02_派生_贸易知识图谱RDF \
  -Dgraph.clear=true
```

> 导入耗时取决于磁盘；940 MB / 276 个文件实测约 14 分钟。
> **不要**用 `deliverables/查询工具/apache-jena-fuseki-5.4.0` 的 tdbloader——那是 TDB2 格式，与运行时读的 TDB1 不兼容。

**导入目标是「命名图」而不是默认图**（应用侧从不读默认图，整个 `backend-main/src/main`
里 `getDefaultModel` 出现 0 次）。目标命名图默认取该本体在库里的真实 URI，
可用 `-Dgraph.named=` 覆盖。这个 URI 有个坑，务必先读 **§11.1**。

**先停后端再导入**：Jena TDB 是单写者（见 §10.4），导入期间不要有别的进程在写
`runtime/ontology-graph-store`。

### 4.4 构建

```bash
bash deploy/build.sh
```

脚本依次做：`mvn package` 主后端 → `mvn package` 训练后端 → 前端 `npm ci` + `npm run build`。

产物：两个 jar + `src/frontend-vue/dist/`。

> **`npm ci` 是必需的**：§4.0 特意排除了 `node_modules`（Windows 原生模块在 Linux 不可用），所以首次构建必须重新安装依赖，这一步需要能访问 npm 源。
> 若前端构建在服务器上 OOM 或失败，可在开发机先构建好，再用 `python deploy/package-for-server.py --with-dist` 打包，只上传 `dist/`。

### 4.5 启动后端

```bash
bash deploy/start-all.sh
```

脚本会把工作目录切到项目根后再启动 Java，因此 `${trade.home}` 自动等于项目根。可用环境变量覆盖关键配置：

```bash
export TRADE_HOME=/opt/trade
export PYTHON_EXE=/usr/bin/python3          # Flask 用哪个解释器
export QWEN_BASE_URL=http://127.0.0.1:8000/v1   # 大模型推理服务地址
bash deploy/start-all.sh
```

### 4.6 配置 Nginx

```bash
sudo cp deploy/nginx/proxy_params_trade.conf /etc/nginx/
sudo cp deploy/nginx/trade.conf /etc/nginx/conf.d/trade.conf
sudo vi /etc/nginx/conf.d/trade.conf     # 改 root 指向真实的 dist 目录
sudo nginx -t && sudo nginx -s reload
```

> **为什么必须配 Nginx**：前端所有请求都以相对路径发出（`src/utils/request.js` 的 `baseURL` 为空字符串），开发环境靠 `vue.config.js` 的 devServer.proxy 转发，生产环境必须由 Nginx 承担同样职责，否则前端一部署就全面 404。

### 4.7 （可选）配置开机自启

`start-all.sh` 适合手动与调试。生产建议用 systemd，示例：

```ini
# /etc/systemd/system/trade-main.service
[Unit]
Description=Trade Backend Main
After=network.target mysql.service

[Service]
Type=simple
User=trade
WorkingDirectory=/opt/trade
Environment=TRADE_HOME=/opt/trade
ExecStart=/usr/bin/java -jar /opt/trade/src/backend-main/target/backend-main-1.0.0.jar
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

> `WorkingDirectory=/opt/trade` 是关键——它是 `${trade.home}` 的默认来源。

## 5. 路径与配置：为什么不用改绝对路径

项目原先在配置里写死了开发机的盘符路径（`D:/Code/Trade/...`、`D:/ontology-graph-store`、`D:\programs\Python\Python310\python.exe` 等）。**本次已全部改造为可移植形式**：

### 5.1 统一基准：`trade.home`

`src/backend-main/.../application.yaml` 与 `src/backend-training/.../application.yml` 顶部都定义了：

```yaml
trade:
  home: ${TRADE_HOME:${user.dir}}
```

含义：优先读环境变量 `TRADE_HOME`；未设置时取 Java 进程的工作目录。所以只要**在项目根启动进程**，所有路径自动正确。

### 5.2 派生路径一览

| 配置项 | 位置 | 默认值 |
|---|---|---|
| 上传目录 | `application.yaml` → `upload.file.location` | `${trade.home}/runtime/uploadFiles/` |
| 图库存储 | `application.yaml` → `ontology.graph.store-path` | `${trade.home}/runtime/ontology-graph-store` |
| 本体文件 | `application.yaml` → `ontology.schema-path` | `${trade.home}/deliverables/本体与映射规则/trade（protege建模导出）.rdf` |
| Python 解释器 | `application.yml` → `python.interpreter` | `${PYTHON_EXE:python}`（走 PATH） |
| 训练脚本目录 | `application.yml` → `python.script.base-path` | `${trade.home}/src/backend-training/python-scripts` |
| 训练 CSV | `application.yml` → `python.data.*.csv-path` | `${trade.home}/src/backend-training/data/{进口,出口}/*.csv` |

### 5.3 其余已改造项

| 位置 | 原值 | 现值 |
|---|---|---|
| 5 个 Java 测试类 | `"D:/Code/Trade"` | `System.getProperty("trade.workspace", "../..")`，pom 注入 |
| `OntologyConfig.java` | `"D:/Code/Trade/deliverables/..."` | `"deliverables/..."`（相对） |
| `OntologyGraphConfig.java` / `JenaGraphRepositoryImpl.java` | `"D:/ontology-graph-store"` | `"runtime/ontology-graph-store"`（相对） |
| `check_mysql.bat` | `cd /d "D:\Code\Trade\..."` | `cd /d "%~dp0.."`（脚本自身位置） |
| `vue.config.js` | 硬编码 `http://localhost:8080` | `process.env.VUE_APP_BACKEND_URL` |
| `tools/kh-corpus-db/*.py` | `D:\Code\Trade\data\...` | 由 `__file__` 上溯推导项目根 |
| `src/pjcait/**` 配置 | `F:/data/cait/...`、`E:\data\...` | `./data/pjcait/...`（相对） |

> 仍有少量绝对路径出现在 `docs/` 下的文档正文里（讲解用途），不影响运行。

## 6. 部署后验证清单

**最快的方式**——跑一键健康检查，覆盖端口、HTTP 接口、登录、数据库行数与 TDB 是否已导入：

```bash
bash deploy/check-health.sh <MySQL密码>
```

输出 `PASS / FAIL / WARN` 汇总；出现 FAIL 时对照 §9 排查。

**手动逐项验证**（便于定位具体环节，内容与上面相同）：

按顺序执行，全部通过即部署成功。

```bash
# ① MySQL 各表行数（关键表应有真实数据，不是 0）
mysql -u root -p -e "USE foreign_trade_qa_db;
  SELECT 'news_articles' t,COUNT(*) c FROM news_articles
  UNION ALL SELECT 'trade_records',COUNT(*) FROM trade_records
  UNION ALL SELECT 'country_monthly_trade',COUNT(*) FROM country_monthly_trade
  UNION ALL SELECT 'comprehensive_data',COUNT(*) FROM comprehensive_data;"

# ② 后端存活
```

## 11. 图谱可视化的三个陷阱（重要）

这三条是「按 §4.3 导入成功、TDB 里也确实有几百万元组，但图谱页仍画不出东西」的完整解释。
按 1 → 2 → 3 顺序排查。

### 11.1 命名图 URI 会多出一个 `v`

命名图 URI 由 `JenaGraphRepositoryImpl.buildNamedGraphUri()` 拼出：

```java
return namedGraphPrefix + ontologyName + "/v" + version;   // 第 307-309 行
// namedGraphPrefix 默认 http://example.org/ontology/     （application.yaml:53）
```

而库里的种子数据与前端输入框**都自带 `v`**（`schema.sql` 里 `versionNumber='v1.0'`，
前端 placeholder 写「请输入版本号，例如：v1.0」），于是实际生成的是：

```
http://example.org/ontology/中哈贸易知识图谱本体/vv1.0
                                                 ↑↑ 两个 v
```

**先确认真实值再导入**：

```bash
grep -E "resolveNamedGraphUri|graphUri=" logs/backend-main.log | tail -5
mysql -uroot -p"$MYSQL_PASSWORD" -N -B \
  -e "SELECT id, project_name, version_number FROM foreign_trade_qa_db.ontology;"
```

导入脚本（`RdfBulkImportTest`）已把目标命名图**默认设成上面这个 URI**，
可用 `-Dgraph.named=` 覆盖；传空串则退回导入默认图（**应用读不到**）。
`getVisualizationData()` 第一件事就是 `containsNamedModel()`，图名对不上会直接返回空。

**为什么不改种子值**：改 `schema.sql` 的 `'v1.0'` 会影响已导入数据的可读性，须连 TDB 一起重建。
已改用 §11.2 的版本回退来消解这个歧义。

### 11.2 可视化接口原先没有版本回退（已修复）

两个接口解析命名图的方式原本**不一致**：

| 接口 | 原行为 |
|---|---|
| 图分析 `/ontology/{id}/graph/**` | 遍历该项目所有版本，找第一个有数据的命名图 —— 健壮 |
| 可视化 `/ontology/{id}/visualization` | 直接用当前版本的 URI —— 版本号写法一变就查到空图 |

现已把前者的逻辑上提为 `OntologyService.resolveNamedGraphUri(Long)`，两处共用
（`GraphAnalysisController.getNamedGraphUri()` 只做转发）。版本号对不上时会自动回退到
有数据的那个命名图。

### 11.3 数据的类型断言不是 OWL 词汇（节点为 0 的根因）

`getVisualizationData()` 原本用这两条查询取节点：

```sparql
?class      a <http://www.w3.org/2002/07/owl#Class>
?individual a <http://www.w3.org/2002/07/owl#NamedIndividual>
```

而 `data/02_派生_贸易知识图谱RDF` 的实际类型断言是**自定义类**：

| 类型 | 实测条数 |
|---|---|
| `vocab#货物` | 1,963,097 |
| `vocab#Property` | 817 |
| `vocab#Class` | 272 |
| `owl:Class` / `owl:NamedIndividual` | **0** |

两条查询都是空集 → `nodes` 为空。而边查询是无上限的全图扫描
（`?s ?p ?o` + `isIRI(?o)`，没有 `LIMIT`），于是产出 1,459,728 条边、
**响应体 302 MB**，且边两端 ID 由 `getLocalNameFromUri` 兜底拼出、
在节点集合里根本不存在 —— 全部悬空。

**修复方案（已实施）**：把 `getVisualizationData()` 改成「类型聚合 + 抽样」——
按 `rdf:type` 聚合出类节点（带实例总数，按 localName 归一，因为 277 个类型 URI 里
有 275 个的 localName 都是「货物」）、每类抽样 Top-N 实例、补一层一步可达的对端节点，
**边只连在已选中节点之间**（故不会悬空），全部查询加 `LIMIT` 与 30s 超时，
真实总量写进 `statistics`。

> ⚠️ 不要用「导入时给每个资源补 `owl:NamedIndividual`」来解决：那会让节点数变成
> 约 196 万，响应体从 302 MB 涨到 GB 级，前端与 JVM 都扛不住。

### 11.4 前端曾有假数据兜底（已移除）

`src/frontend-vue/src/views/DataVisualization.vue` 原先在**节点为空**或**接口异常**时
调用 `generateMockData()` 画出编造的图谱 —— `产品/供应商/订单/客户`、`iPhone 15`、
`MacBook Pro`、`富士康`、`比亚迪`、`订单2024001`、`张三`、`李四`，只弹一个
`message.warning('该本体暂无图谱数据，使用示例数据展示')`。

**结项演示时这会造成「看起来有数据、实则全部虚构」**，与 `InitDataController` 写
`Math.random()` 属同一类问题，现已彻底移除：改为清空图谱并显示空状态覆盖层
（模板里 `empty-chart-overlay` 本来就有，只是被假数据顶掉了）。
`generateMockData()` 函数本身也已删除，避免留下 `no-unused-vars` 死代码。
