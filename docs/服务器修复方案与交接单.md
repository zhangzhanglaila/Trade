## 1. 【P0】把服务器上的 5 处修复回灌到 Git 仓库

### 1.1 为什么这是 P0

服务器拷贝是「仓库 + 5 处临时修复」。如果之后有人 `git clone` 或解包一份新的
`trade-server-<日期>.tar.gz` 覆盖上去，这 5 处修复**会静默消失**，一切回到原点。
所以第一件事是把它们变成仓库里的正式改动。

### 1.3 关于第 3 条的③：这是「图谱页空白」的必改项

已核实代码现状（`RdfBulkImportTest.java`）：

```java
// 第 119 行 —— 写默认图
Model target = dataset.getDefaultModel();
```

而应用读的是**命名图**。命名图 URI 由 `JenaGraphRepositoryImpl.buildNamedGraphUri()` 生成：

```java
// JenaGraphRepositoryImpl.java:307-309
public String buildNamedGraphUri(String ontologyName, String version) {
    return namedGraphPrefix + ontologyName + "/v" + version;
}
// namedGraphPrefix 默认 http://example.org/ontology/  （application.yaml:53）
```

而 `getVisualizationData()` 第一件事就是判断这个命名图在不在：

```java
// JenaGraphRepositoryImpl.java:1338
if (!dataset.containsNamedModel(namedGraphUri)) {
    return ... nodes=[], edges=[]      // 直接返回空，连查询都不做
}
```

**→ 不写进正确的命名图，图谱页必然空白。** 服务器那轮已经把导入改成写命名图了（否则不会观察到 146 万条边），
但**导入目标 URI 必须与 `buildNamedGraphUri` 的输出逐字节一致**，这里有个陷阱见 **§3.1**。

## 2. 【P0】图谱可视化页的修复方案（核心问题）

### 2.1 现象（服务器实测）

```
GET /ontology/1/visualization
→ nodes: []  +  edges: 146 万条，响应体 302 MB
```

### 2.2 根因：三条查询逐条分析

`JenaGraphRepositoryImpl.getVisualizationData()`（第 1323 行起）依次跑三条查询，
写成「类节点 + 实例节点 + 关系边」的本体式结构，但这批数据**不是本体式 RDF**。

**① 类节点查询 —— 查到 0 个**（第 1347-1354 行）

```sparql
?class a <http://www.w3.org/2002/07/owl#Class>
```

**② 实例节点查询 —— 查到 0 个**（第 1401-1408 行）

```sparql
?individual a <http://www.w3.org/2002/07/owl#NamedIndividual>
```

而 `data/02_派生_贸易知识图谱RDF/` 的实际数据长这样（实测样本
`2015_11_12_Kazakhstan_exit_mapped_data.rdf`）：

```xml
<rdf:Description rdf:about="http://F:/Trade/data/哈萨克斯坦/出口/2015.11—12.csv.com/货物/室内除臭制品">
  <vocab:仓储位置 rdf:resource="http://F:/Trade/data/哈萨克斯坦/出口/2015.11—12.csv.com/仓库/浙江省"/>
  <vocab:发货日期 rdf:datatype="http://www.w3.org/2001/XMLSchema#gYearMonth">2015-11</vocab:发货日期>
  <vocab:商品编码 rdf:datatype="http://www.w3.org/2001/XMLSchema#string">33074900</vocab:商品编码>
  <rdf:type rdf:resource="http://F:/Trade/data/哈萨克斯坦/出口/2015.11—12.csv.com/vocab#货物"/>
</rdf:Description>
```

类型断言是 **`vocab#货物`**（自定义类，实测约 196 万条），**没有任何 `owl:Class` / `owl:NamedIndividual`**。
两条查询都返回空集 → `nodes` 为空。

**③ 关系边查询 —— 无上限全图扫描**（第 1454-1463 行）

```sparql
?source ?prop ?target .
FILTER (isIRI(?target))
FILTER (?prop != rdf:type)
FILTER (?prop != rdfs:subClassOf)
-- 没有 LIMIT
```

356 万条三元组里绝大多数是 `货物 --仓储位置--> 仓库` 这种 IRI→IRI 三元组，
于是产出 146 万条边。又因为 `allNodesIdMap` 是空的，边两端退化成
`getLocalNameFromUri()` 拼出的 ID（第 1490-1495 行），**这些 ID 在 `nodes` 里根本不存在**。

→ 最终结果：**边全部悬空 + 302 MB 响应体**。前端拿不到任何可画的节点。

**④ 附带发现：前端会兜底显示假数据**（这条比上面更严重）

`src/frontend-vue/src/views/DataVisualization.vue`：

```javascript
// 第 1110-1118 行
} else {
  message.warning('该本体暂无图谱数据，使用示例数据展示')
  const data = generateMockData()      // 第 759 行定义
  graphData.nodes = data.nodes
  graphData.links = data.links
  renderChart()
}
```

`generateMockData()` 生成的是 **`产品 / 供应商 / 订单 / 客户`、`iPhone 15`、`MacBook Pro`、
`富士康`、`比亚迪`、`订单2024001`、`张三`、`李四`**（第 764-781 行）。

也就是说：**节点为空时，页面不会报错，而是画出一张编造的图谱，只弹一个轻描淡写的提示。**
在结项演示场景下这是「看起来有数据、实则全部虚构」，与 `InitDataController` 写
`Math.random()` 假数据属同一类问题，**必须去掉**。

> 注：`src/frontend-vue/src/views/OntologyProject.vue`（第 1478 行 `loadVisualizationData`）
> **没有**这个兜底，可以照它改。

### 2.3 一个必须先讲清的认知

**「导入时补 `owl:NamedIndividual`」单独用，解决不了问题，反而会更糟。**

- 它确实能让第 ② 条查询查到节点 —— 但会一次返回约 **196 万个节点**。
- 302 MB 会变成 GB 级，前端 ECharts 必然崩，JVM 也吃不消（当前代码把 146 万个 `EdgeDTO`
  对象全部堆在 `List` 里再序列化，见第 1499-1507 行）。
- 而且要给 TDB 额外写入约 196 万条冗余三元组。

**真正的矛盾是「196 万节点的全图渲染不成立」**，不是「查询条件写错了」。所以修复的落点是
**数据驱动的类型聚合 + 有上限的抽样**，而补断言最多只能作为辅助。

### 2.4 三个方案对照

| | **方案甲 · 类型聚合 + 抽样（推荐）** | **方案乙 · 补类型断言** | **方案丙 · 改前端截断** |
|---|---|---|---|
| 做法 | 重写 `getVisualizationData`：先按 `rdf:type` 聚合出"类节点"（带实例总数），每类抽样 Top-N 实例，边只在选中节点之间取，且加 `LIMIT` | 导入时为每个资源补 `a owl:NamedIndividual`、为每个类型补 `a owl:Class` | 后端不动，前端把 nodes/edges 截断到 500/2000 |
| 结果 | 节点/边规模可控（数百量级），语义正确，显示真实总量 | 查到 196 万节点 → 响应爆炸、前端崩 | 后端仍生成 302 MB 响应，传输与 JVM 内存问题依旧 |
| 改动量 | 中（1 个方法，约 100 行内） | 小 | 极小 |
| 解决「节点为 0」 | ✅ | ✅ | ❌ |
| 解决「302 MB」 | ✅ | ❌（更糟） | ❌ |
| 结论 | **必做** | 单独做**无效**，不建议 | 仅可作临时缓解，不推荐 |

**推荐组合**：**方案甲（必做）** + 去掉前端假数据兜底（§2.6）。
若结项展示时间允许，可再加「**图谱概览页**」形态（统计卡片 + 局部子图，
按"国家 + 品类"逐步展开），这比"一张全图"更适合 356 万条三元组的数据量级。

### 2.5 方案甲的具体实现

改动集中在 `JenaGraphRepositoryImpl.getVisualizationData()`（第 1323-1524 行），
把内部三条查询换成下面四步。**不要在 SPARQL 里硬编码 `货物`**，类型全部从数据里来。

```java
// ── 第 1 步：类型聚合（替代原第 1347-1354 行的 classQuery）
// 输出「类节点」：每个 rdf:type 一个节点，标签带实例总数
String typeQuery =
    "SELECT ?type (COUNT(?s) AS ?cnt) WHERE { " +
    "  GRAPH <" + namedGraphUri + "> { ?s a ?type } " +
    "  FILTER (isIRI(?type)) " +
    "} GROUP BY ?type ORDER BY DESC(?cnt) LIMIT 50";

// ── 第 2 步：每类抽样 Top-N 实例（替代原第 1401-1408 行的 individualQuery）
// PER_TYPE_LIMIT 建议 100；只对前 5~8 个类型抽样，避免总节点数失控
String sampleQuery =
    "SELECT ?s WHERE { " +
    "  GRAPH <" + namedGraphUri + "> { ?s a <" + typeUri + "> } " +
    "} LIMIT " + PER_TYPE_LIMIT;

// ── 第 3 步：只在已选中节点之间取边（替代原第 1454-1463 行）
// 关键：用 VALUES 把两端都限死在已选节点集合内，并加 LIMIT
String edgeQuery =
    "SELECT ?s ?p ?o WHERE { " +
    "  GRAPH <" + namedGraphUri + "> { ?s ?p ?o } " +
    "  FILTER (isIRI(?o)) " +
    "  FILTER (?p != <" + RDF.type.getURI() + ">) " +
    "  VALUES ?s { " + selectedUriList + " } " +
    "  VALUES ?o { " + selectedUriList + " } " +
    "} LIMIT " + EDGE_LIMIT;      // 建议 5000

// ── 第 4 步：把真实总量与被截断事实写进 statistics（DTO 已有该字段，见下）
dto.getStatistics().put("totalTriples", ...);
dto.getStatistics().put("totalInstances", ...);
dto.getStatistics().put("truncated", true);
dto.getStatistics().put("sampledNodes", nodes.size());
```

要点：

1. **`LIMIT` 必须加**。第 2 步的抽样靠 `LIMIT` 让 Jena 提前终止；第 3 步靠 `VALUES` 把
   候选集降到数百个，再 `LIMIT` 兜底。
2. **`VALUES` 的 URI 必须转义**。这批数据的 IRI 里有中文、全角逗号、破折号，还可能残留
   裸 `%` 与 `[]`（第 3 条修复已在处理）。拼 `VALUES` 前统一走一次转义函数。
3. **加超时保护**：`QueryExecutionFactory` 之后调 `qexec.setTimeout(30_000, TimeUnit.MILLISECONDS)`，
   避免个别查询拖死请求。
4. **`statistics` 字段已经存在**，不用改 `OntologyVisualizationDTO`：
   ```java
   // OntologyVisualizationDTO.java:22
   private Map<String, Object> statistics;
   ```
5. **JVM 堆**：即使抽样后，也建议给 8080 进程 `-Xmx2g` 以上；改之前堆压力主要来自
   146 万个 `EdgeDTO` 对象。
6. **可视化接口缺少版本回退**（与图分析接口不一致），见 **§3.2**，建议一并修。

### 2.6 必须同步做的：去掉前端假数据兜底

| 行 | 现状 | 改为 |

## 3. 【P1】本次新发现的两个坑（报告未覆盖）

### 3.1 命名图 URI 会多出一个 `v`（`/vv1.0`）

- URI 模板：`namedGraphPrefix + ontologyName + "/v" + version`（`JenaGraphRepositoryImpl.java:308`）
- 而库里种子数据和前端提示**都自带 `v`**：
  ```sql
  -- src/backend-main/src/main/resources/db/schema.sql:186
  SELECT '中哈贸易知识图谱本体', 'admin', 'v1.0', ...
  ```
  ```html
  <!-- src/frontend-vue/src/views/OntologyManagement.vue:117 -->
  <a-input v-model:value="form.version" placeholder="请输入版本号，例如：v1.0" />
  ```

**→ 实际生成的 URI 是 `http://example.org/ontology/中哈贸易知识图谱本体/vv1.0`（两个 v）。**

这不是必须改代码的 bug，但**导入 RDF 时必须按应用真实生成的 URI 写**，否则 §1.3 那条
`containsNamedModel` 判断会直接返回空。

**排查方法**（先确认真实值再导入）：

```bash
# 看后端启动日志里的实际 URI
grep -E "getVisualizationData: querying graph|graphUri=" logs/backend-main.log | tail -5
# 或直接查库里的本体记录
mysql -uroot -p"$MYSQL_PASSWORD" -N -B \
  -e "SELECT id, project_name, version_number FROM foreign_trade_qa_db.ontology;"
```

然后用下面的 SPARQL 列出 TDB 里**实际存在**的命名图，确认两边一致：

```sparql
SELECT DISTINCT ?g WHERE { GRAPH ?g { ?s ?p ?o } }
```

**建议**：仓库里把 `schema.sql` 的种子版本号改成 `'1.0'`（去掉 `v`），并修正前端
placeholder 文案，消除这个歧义。若你决定改，**注意 TDB 里的命名图名要同步**，否则已导入的数据会读不到。

### 3.2 可视化接口没有版本回退，图分析接口有

两个接口解析命名图的方式**不一致**：

| 接口 | 解析方式 | 行为 |
|---|---|---|
| 图分析 `/ontology/{id}/graph/**` | `GraphAnalysisController.getNamedGraphUri()`（第 307-340 行）**遍历该项目所有版本**，找到第一个存在的命名图 | 健壮 |
| 可视化 `/ontology/{id}/visualization` | `OntologyServiceImpl.getOntologyVisualization()`（第 1497-1502 行）**直接用当前版本的 URI** | 一旦版本号对不上就是空 |

**建议**：把 `GraphAnalysisController.getNamedGraphUri()` 的逻辑提到共用的地方，
让可视化接口也走「遍历版本找有数据的图」。这样能顺带消掉 §3.1 带来的大部分风险。

## 4. 【P1】数据问题处理方案

### 4.1 三个截断 RDF —— **可以救，实测通过**

报告说"3 个 RDF 被截断无法解析"，实际复核后**结论要更正：丢掉最后 1 条残缺描述后，
其余 99.2%~99.9% 完全可用**。三个文件都是在最后一个 `<rdf:Description>` 中途被切断的
（尾部停在 `rdf:datatype=` 一半处）。

实测修复结果（已在开发机验证 XML 良构性）：

| 文件 | 原始 | 修复后 | 丢弃 | 保留比例 | 补 `</rdf:RDF>` 后 XML |
|---|---|---|---|---|---|
| `2015_11_12_Kazakhstan_exit_mapped_data.rdf` | 870,045 B | 869,237 B | 808 B | **99.91%** | ✅ 良构 |
| `2016_11_12_Kyrgyzstan_exit_mapped_data.rdf` | 159,549 B | 158,310 B | 1,239 B | **99.21%** | ✅ 良构 |
| `2017_9_12_Tajikistan_exit_mapped_data.rdf` | 1,168,843 B | 1,168,069 B | 774 B | **99.93%** | ✅ 良构 |

**修复脚本**（幂等，先备份再改；建议在开发机改好后重新打包，服务器上直接解包）：

```python
from pathlib import Path
import shutil

RDF_DIR = Path('data/02_派生_贸易知识图谱RDF')
NAMES = [
    '2015_11_12_Kazakhstan_exit_mapped_data.rdf',
    '2016_11_12_Kyrgyzstan_exit_mapped_data.rdf',
    '2017_9_12_Tajikistan_exit_mapped_data.rdf',
]

for name in NAMES:
    p = RDF_DIR / name
    data = p.read_bytes()
    if data.rstrip().endswith(b'</rdf:RDF>'):
        print('已修复，跳过:', name); continue
    shutil.copy2(p, p.with_suffix('.rdf.bak'))       # 先备份
    cut = data.rfind(b'</rdf:Description>')
    if cut < 0:
        print('!! 找不到完整描述，人工处理:', name); continue
    repaired = data[:cut + len(b'</rdf:Description>')] + b'\r\n</rdf:RDF>\r\n'
    p.write_bytes(repaired)
    print(f'{name}: {len(data)} -> {len(repaired)} (丢弃 {len(data)-len(repaired)} B)')
```

改完后再跑图谱导入，**"失败 3 个"应变成 0**。

> 这批文件在 `data/`，**本来就不入 Git**（见 `docs/版本控制说明.md`）。所以修好后要么重新打
> `trade-server-<日期>.tar.gz` 上传，要么在服务器上就地修。

### 4.2 两个零填充 CSV —— 结构比报告描述的更复杂

报告说"各含 718 KB 连续零填充，且二者 MD5 相同"。复核确认，并进一步查清了内部结构：

**文件**：`data/01_原始_海关进出口明细/哈萨克斯坦/出口/2021.7—8.csv`
与 `2021.9—10.csv`
**两者字节完全相同**：均为 1,375,492 B，MD5 均为 `a2c4fe4628f7a1a59adc6a07736ea19a`

**内部分三段**（实测）：

| 段 | 范围 | 长度 | 占比 | 内容 |
|---|---|---|---|---|
| 前置段 | 0 – 288,998 | 289 KB | 21.0% | 文本，**9 列**格式，3,160 行数据 |
| NUL 段 | 288,998 – 1,007,594 | **718,596 B** | **52.2%** | 全 `\x00` |
| 后置段 | 1,007,594 – 末 | 368 KB | 26.7% | 文本，**14 列**标准格式，2,639 行数据 |

**关键发现一：前置段与后置段的表头不同，不能作为一个文件导入。**

- 前置段表头（**9 列**）：`商品编码,商品名称,贸易伙伴编码,贸易伙伴名称,第一数量,第一计量单位,第二数量,第二计量单位,人民币`
  —— **缺 `数据年月`、缺 `注册地编码/名称`、缺 `贸易方式`**
- 后置段表头（**14 列**，与全库主流一致）：
  `数据年月,贸易伙伴编码,贸易伙伴名称,商品编码,商品名称,贸易方式编码,贸易方式名称,注册地编码,注册地名称,第一数量,第一计量单位,第二数量,第二计量单位,人民币`

我把全库 295 个 CSV 的表头做了归组普查，结果：

| 表头格式 | 文件数 |
|---|---|
| 14 列（两种列序） | 210 |
| 15 列（含 `备注`） | 12 |
| 单列/其他（多为误命名的 xlsx） | 71 |
| **9 列** | **2 —— 只有这两个损坏文件** |

**→ 9 列格式在全数据集中是孤例**，且缺少 `init_mysql.py` 取值所需的
`注册地名称` / `贸易方式编码` 等字段（见 `deploy/init_mysql.py:239-246`）。
按它导入会得到大量 NULL 字段的残缺记录。

**关键发现二：这两个文件的数据其实都是 2021 年 7—8 月。**

后置段的 `数据年月` 分布实测为：`202107` 91 行 + `202108` 2,548 行。

**→ 结论：`2021.7—8.csv` 的文件名与内容相符；`2021.9—10.csv` 是它的错误副本，
2021 年 9—10 月的出口数据实际缺失。**

**处置建议**（按优先级）：

1. **不要试图原样导入**——`csv` 模块遇到 NUL 会直接抛错（这正是 §1 第 1 处修复在处理的）。
2. **可用的真实数据 = 后置段**：剥离 NUL 后，取第 1,007,594 字节起的 14 列段，
   2,639 行，导入 `trade_records`（走 `csv.DictReader` 按表头名取值即可）。
3. **前置段建议隔离**：3,160 行、无日期与注册地、格式全库唯一 → 无法归属到任何时段，
   建议**不入库**，或单独落到一张 `quarantine` 表留档。若结项材料需要凑行数，
   必须注明这 3,160 行来源存疑。
4. **`2021.9—10.csv` 建议重命名或加注**（如 `2021.9—10.csv.duplicate-of-2021.7—8`），
   并在结项文档中写明 **2021 年 9—10 月哈萨克斯坦出口数据缺失**，避免被追问时说不清。

**核查用命令**：

```bash
# 确认两个文件确实同源
md5sum data/01_原始_海关进出口明细/哈萨克斯坦/出口/2021.7—8.csv \
       data/01_原始_海关进出口明细/哈萨克斯坦/出口/2021.9—10.csv

# 定位 NUL 段边界
python3 -c "
d=open('data/01_原始_海关进出口明细/哈萨克斯坦/出口/2021.7—8.csv','rb').read()
i=d.find(b'\x00'); j=i
while j<len(d) and d[j]==0: j+=1
print('NUL 段:', i, '->', j, '  长度', j-i, '  占', round((j-i)/len(d)*100,1),'%')"
```

### 4.3 其余 32 个含 NUL 的 CSV —— 属正常范围

除上述 2 个外，还有 32 个文件含 NUL，但**每个只有 1~26 个 NUL 字节、最长连续段为 1**，
是数据里零星混入的单个 `\x00`，不是文件损坏。**按行剥离即可**（§1 第 1 处修复已覆盖），
**不需要**当作损坏数据特殊处理。
