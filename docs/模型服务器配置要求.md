# 中哈贸易系统 · 模型服务器配置要求

> 本文数据来自对 `models/` 与 `src/backend-training/python-scripts/model/` 的实际解析
> （safetensors 头部逐张量统计 + `config.json` 推导 KV Cache），非估算模板。
> 文中所有"GiB"= 1024³ 字节，"GB"= 1000³ 字节，权重体积均按 GiB。

---

## 0. 一句话结论

| 场景 | GPU | 内存 | 磁盘 |
|---|---|---|---|
| **推荐**（单卡 24 GB，4-bit 在线量化） | RTX 4090 24G / L4 24G / A10 24G / RTX 3090 24G | 32 GB | 100 GB SSD |
| 全精度 bf16 加载 | 40–48 GB（A100-40G 紧、A6000 48G、L40S 48G） | 64 GB | 100 GB SSD |
| 纯 CPU 降级（无 GPU，量化运行） | 不需要 | 32 GB（**可用内存 ≥ 12 GB**） | 100 GB SSD |
| 只跑预测模型（不跑问答大模型） | 不需要 | 8 GB | 30 GB |

**关键点：24 GB 单卡不是我的建议值，而是模型作者在项目里已经写定的目标平台** ——
`models/qwen3.5-9b-kh-trade-qa/configs/serve_vllm_merged.yaml` 的注释原文是
「单卡 24GB 使用 bf16 合并权重时，推荐保持 bitsandbytes 4-bit 在线量化」。
照这个配置走，兼容性风险最低。

## 1. 这个系统里有三个模型，别把它们混在一起算

| # | 模型 | 文件 | 参数量 / 体积 | 跑在哪里 | 是否必需 |
|---|---|---|---|---|---|
| 1 | **Qwen3.5-9B 中哈贸易物流问答**（已合并 QLoRA 的完整权重） | `models/qwen3.5-9b-kh-trade-logistics-merged-v1/`，4 个 safetensors | **9.41 B 参数 / 17.53 GiB** | 独立推理服务（vLLM / ollama），OpenAI 兼容接口 | 问答功能的**LLM 兜底**需要；缺它时问答退化为只走关键词路由 |
| 2 | **trade_Transformer 进出口预测**（price / quantity 各一套，in+out 两份） | `src/backend-training/python-scripts/model/trade_Transformer/{in,out}/*.pth` | 4 × 14.3 MB + 8 个 `.pkl` ≈ 115 MB | Flask 5000 进程内（torch） | 已接入，**CPU 即可**，不占显存 |
| 3 | **嵌入模型**（向量检索用） | **项目未随附**，需自备 | 视所选模型而定 | 与 Milvus 配套 | 仅向量检索需要。`application.yaml` 里 `MILVUS_DIMENSION=1024`，要选**输出 1024 维**的嵌入模型 |

**只有 1 号需要认真配 GPU**。2 号是 14 MB 级的小模型，3 号通常是 0.6 B 级嵌入模型（显存 1–2 GiB 或直接走 CPU）。

## 2. 一号模型的实测规格

从 `config.json` 与 4 个 safetensors 头部逐张量统计得出：

| 项 | 实测值 |
|---|---|
| 架构 | `Qwen3_5ForConditionalGeneration`（**多模态 VLM**，带 `vision_config`） |
| 总参数量 | **9,409,813,744（9.41 B）** |
| 权重精度 | 全部 **BF16**（4 个分片无一例外） |
| 权重实际体积 | **17.527 GiB**（元数据 `total_size` = 18,819,627,488 字节） |
| 参数分布 | language 7.94 B（84.3%）· lm_head+embedding 1.02 B（10.8%）· **vision tower 0.456 B（4.8%）** |
| 文本层数 | 32 层 = **24 层 linear attention + 8 层 full attention**（混合线性注意力） |
| 注意力 | 16 个 Q head / **4 个 KV head**（GQA 4:1），head_dim 256 |
| 词表 | 248,320 |
| 原生最大上下文 | 262,144（256 K） |
| 视觉塔 | depth 27，hidden 1152，输出 4096（与文本 hidden 对齐） |
| 服务时实际上下文 | 项目配置只开 **4096**（`max-model-len: 4096`） |

### KV Cache 实测推导（这是本模型最省显存的地方）

因为 32 层里只有 **8 层**是全注意力、其余 24 层是 linear attention 不需要 KV Cache：

```
每 token 每层 KV = 2(K,V) × 4(kv_heads) × 256(head_dim) × 2 字节 = 4.0 KiB
只有 8 层需要            → 每 token 合计 32.0 KiB
```

| 上下文长度 | KV Cache（batch=1） |
|---|---|
| 4,096 | 128 MiB |
| 8,192 | 256 MiB |
| 32,768 | 1 GiB |
| 131,072 | 4 GiB |
| 262,144 | 8 GiB |

**含义**：把上下文从 4096 提到 32768，显存只多花约 0.9 GiB。这是该架构的红利 ——
如果你的问答要带长 RAG 上下文，完全可以放心开大，瓶颈在权重而不在 KV。

## 3. 显存怎么算（权重 + 框架开销 + KV）

| 方案 | 权重占用 | 框架/激活/CUDA Graph | KV(4096) | **建议可用显存** | 对应显卡 |
|---|---|---|---|---|---|
| **4-bit NF4**（项目推荐配置） | ≈ 5.5–7 GiB | 2–4 GiB | 0.125 GiB | **≥ 8–11 GiB** | **24 GB 宽裕**；16 GB 可行；12 GB 勉强需调参 |
| bf16 全精度 | 17.53 GiB | 3–5 GiB | 0.125 GiB | **≥ 21–23 GiB** | 24 GB 余量很小（故项目改用 4-bit）；**40 GB+ 才稳** |
| Q4_K_M GGUF（llama.cpp 系） | ≈ 5.7 GiB（走内存） | 1–2 GiB | 随上下文 | 系统可用内存 ≥ 12 GiB | 无需 GPU |

补充几点：

- **4-bit 下 16 GB 显卡也能跑**。按上表，权重 + 开销 + KV 约 9–11 GiB，16 GB 有富余空间；
  把 `--gpu-memory-utilization` 从 0.90 调到 0.80 左右即可。12 GB 是下限，需要同时压
  `max-model-len`，不建议生产用。
- **加载峰值在内存上，不在显存上**。bitsandbytes 是"在线量化"——先把 17.53 GiB 的 bf16 权重读进
  内存再转 4-bit，所以**系统内存建议 32 GB**，16 GB 会在加载阶段 OOM。
- **vision tower 占 0.456 B（4.8%）**，为它单独做裁剪不划算，正常加载即可。
- 想省显存的替代路线：AWQ / GPTQ 离线量化（需自行转换，且依赖 vLLM 对该架构的支持）；
  多卡 tensor parallel 对这种规模不划算。

## 4. 三档方案对照

| | **A · 推荐（4-bit / 24 GB）** | **B · 全精度（bf16）** | **C · 纯 CPU 降级** |
|---|---|---|---|
| GPU | 单卡 24 GB（4090 / L4 / A10 / 3090） | 单卡 40–48 GB | 无 |
| 显存占用 | 约 9–11 GiB 峰值 | 约 21–23 GiB | — |
| 系统内存 | **32 GB** | **64 GB** | **32 GB**（可用 ≥ 12 GB） |
| 磁盘 | 100 GB SSD | 100 GB SSD | 100 GB SSD |
| CPU | 8 核（4 核可跑，加载偏慢） | 8 核 | **16 核** |
| 预期吞吐 | 单流通常数十 tok/s 量级 | 同量级，略优 | 明显更慢（个位数 tok/s 量级） |
| 风险 | 低（与项目配置一致） | 显存余量小 | 该架构在 llama.cpp 系的支持**未经验证** |
| 适合 | **正式部署** | 有现成 40G+ 卡 | 只是演示 / 没钱买卡 |

> 吞吐量级仅为经验参考。**以实际硬件压测为准**，验收命令见 §8。
> 影响速度的主因是显存带宽与是否 4-bit，不是 CPU 核数。

## 5. 磁盘与网络

| 项 | 体积 | 说明 |
|---|---|---|
| Qwen 权重 | 17.53 GiB | 4 个分片缺一不可，另需 `model.safetensors.index.json` + `config.json` + tokenizer |
| HF 缓存冗余 | ≈ 17.5 GiB | 用 `hf download` 下载时会额外占一份缓存，预留双份更稳 |
| 项目代码（解包后） | ≈ 2.5 GB | 来自 `deploy/package-for-server.py` 的交付包 |
| TDB 图库 | 2–3 GB | 导入 940 MB RDF 之后 |
| MySQL 数据目录 | 2–4 GB | 234 万行贸易明细 + 语料 |
| Python / torch / CUDA 依赖 | 5–10 GB | vLLM 及 CUDA 运行库体积不小 |
| **合计建议** | **≥ 100 GB SSD** | 不要用机械盘跑推理 |

**下载渠道**：模型发布在 Hugging Face（`xidrug/qwen3.5-9b-kh-trade-logistics-merged-v1`）。
国内服务器若访问不稳，用镜像：`export HF_ENDPOINT=https://hf-mirror.com`。

**开发机侧提醒**：`deploy/package-for-server.py --with-models` 会额外打 17.8 GB，
打包过程需要约 2 倍峰值空间；本机 D 盘剩余空间不足 19 GB，**不要在本机执行 `--with-models`**，
模型请走 HF 下载或单独传输。

## 6. 软件栈

| 组件 | 要求 | 说明 |
|---|---|---|
| NVIDIA 驱动 | ≥ 550 系列 | 需匹配 CUDA 12.x |
| CUDA | 12.1 – 12.8 | 随 vLLM 的 wheel 走，通常无需单独装 toolkit |
| Python（**推理服务独立 venv**） | **3.10 – 3.12** | vLLM 不支持 3.9。注意主后端的 Flask 用的是 3.9–3.10，**两者环境要隔离** |
| vLLM | 较新版本 | 必须支持 `Qwen3_5ForConditionalGeneration` |
| transformers | ≥ 5.8.0 | 与模型 `transformers_version` 对齐；低于此版本可能不识别 `qwen3_5` |
| bitsandbytes | ≥ 0.45 | 4-bit 在线量化依赖它 |
| 推理端口 | 8000（默认） | 后端通过 `QWEN_BASE_URL` 指向它 |

启动方式（模型权重已在本地时，把 `model` 换成绝对路径即可）：

```bash
# 方式一：用项目自带配置（推荐）
cd models/qwen3.5-9b-kh-trade-qa
vllm serve --config configs/serve_vllm_merged.yaml

# 方式二：等价命令行
vllm serve /opt/trade/models/qwen3.5-9b-kh-trade-logistics-merged-v1 \
  --served-model-name qwen3.5-9b \
  --host 0.0.0.0 --port 8000 \
  --dtype bfloat16 --quantization bitsandbytes \
  --gpu-memory-utilization 0.90 --max-model-len 4096
```

> 项目原配置的 `host` 是 `127.0.0.1`，**只监听本机**。若要给别的机器访问，改成 `0.0.0.0`，
> 并且**必须**在网关层补认证 / TLS / 限流 —— 这个接口没有任何鉴权。

后端侧只要两个变量（写在 `config/.env`）：

```bash
QWEN_BASE_URL=http://127.0.0.1:8000/v1
QWEN_CHAT_ENDPOINT=/chat/completions
# 并把 application.yaml 的 ai.qwen.chat.model 填为 qwen3.5-9b
```

## 7. 与主系统同机部署时的整机配置

问答大模型和业务后端**可以放同一台机器**，但要按加起来算：

| 资源消费者 | 内存 / 显存 |
|---|---|
| Qwen 推理服务 | 内存 20–24 GB（加载峰值）+ 显存 9–11 GiB |
| Milvus（向量检索） | 2–4 GB 内存 |
| MySQL 8 | 2–3 GB 内存 |
| 主后端 8080 + 训练后端 8081（2 个 JVM） | 1.5–3 GB 内存 |
| Flask 5000（torch 加载预测模型） | 1–1.5 GB 内存 |
| Nginx + AJ-Report | 0.5–1 GB 内存 |
| **同机合计建议** | **内存 48 GB / 显存 24 GB / 磁盘 150 GB** |

| 部署形态 | 配置 |
|---|---|
| **分两台（推荐）** | 模型机：24 GB GPU + 32 GB 内存 + 100 GB SSD<br>应用机：8 核 / 16 GB 内存 / 100 GB SSD |
| 合一台 | 24 GB GPU + 48 GB 内存 / 150 GB SSD |
| 只求跑起来（不开问答大模型） | 8 核 / 16 GB 内存 / 60 GB SSD，GPU 不需要 |

**分两台的好处**：模型加载和重构（换权重、调 `max-model-len`）不会牵动业务后端；
24 GB 显存的模型机也能随时加卡扩容。

## 8. 风险与未验证项（部署前必读）

1. **⚠️ 架构支持需实测**。本模型 `model_type` 是 `qwen3_5`，且带 `vision_config`（多模态）。
   vLLM / ollama / llama.cpp 对该架构的支持程度**尚未验证**。项目自己的部署文档也标注了这一点。
   下单买卡之前，**先在一台有卡机器上把推理服务跑起来**，别先囤硬件。
2. **仓库里的 `Modelfile` 不一定能用**。它是 LLaMA-Factory 自动生成的
   （`FROM .`、`num_ctx 4096`），并没有验证过能通过 ollama 加载这个 4 分片 VLM。
   走 GPU + vLLM 是风险最低的路径。
3. **首次加载慢**。bitsandbytes 在线量化要先把 17.53 GiB bf16 读进内存再转换，
   首次启动几分钟属正常，不要误判为卡死。
4. **嵌入模型项目没给**。`MILVUS_DIMENSION=1024` 是你必须自己配一个 1024 维嵌入模型
   （推理资源很小，1–2 GiB 显存或纯 CPU 均可）。
5. **不要依赖模型输出 JSON**。官方模型卡写明 JSON 提取专项的合法 JSON 比例为 **0.00%**。
   若你的业务流程需要结构化输出，必须加约束解码或二次校验，不能靠提示词。
6. **256 K 上下文是原生能力，但项目服务只开了 4096**。需要长上下文时改 `max-model-len`，
   KV Cache 成本极低（见 §2 表），但要让 vLLM 预留相应显存。

## 9. 上线验收命令

```bash
# ① 显卡与驱动
nvidia-smi                          # 确认显存容量、驱动版本、CUDA 版本
python -c "import torch;print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"

# ② 推理服务起来了没
curl -s http://127.0.0.1:8000/v1/models | python -m json.tool
#    期望：model 列表里出现 "qwen3.5-9b"

# ③ 真跑一次对话（同时看显存占用）
curl -s http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.5-9b","messages":[{"role":"user","content":"中国出口到哈萨克斯坦需要哪些通关单证？"}],"max_tokens":256,"temperature":0.1}'
nvidia-smi                          # 另开一个终端观察峰值显存

# ④ 后端是否真的接上了
export QWEN_BASE_URL=http://127.0.0.1:8000/v1
bash deploy/check-health.sh
```

吞吐压测（决定你能扛多少并发）：

```bash
vllm bench serve --model qwen3.5-9b --base-url http://127.0.0.1:8000 \
  --num-prompts 100 --max-concurrency 8
```
