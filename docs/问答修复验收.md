## 二、改动

### 路由：两条 → 四条

判定顺序 `CHITCHAT → PREDICT → DATA_QUERY → RAG_NEWS → LLM 四分类`：

- **PREDICT** 必须出现前瞻词（预测 / 预估 / 预计 / 下月 / 未来 / 会是多少 / 明年 …）；
- **DATA_QUERY** 条件为 `贸易词 && (查询词 || 出现年月)`，且**必须排在 RAG 之前**，
  否则「最近三个月…是多少」会被"最近"劫持；数据查询**不把年月缺省成下个月**（预测才缺省）；
- **CHITCHAT**：≤12 字且命中寒暄词，或命中「你是谁 / 你能做什么 / 怎么用」；
- **LLM 兜底提示词同步改为四分类**（这是「你好」被判成预测的直接原因）。

### 历史数据查询（新增 `ai/query/TradeDataQueryService`）

- 复用主 DataSource + 跨库限定名查 `trade` 库，无新增连接配置；
- 商品名解析：精确 → 全串 LIKE（唯一才采用）→ 2-gram 打分 → 单字兜底给候选；
- 未来月份 → 明确说明"库中最新 2025-03"并引导改用预测；
- **未指定商品时不给数量合计**：不同商品计量单位不同（千克/米/台/株…），
  相加会得到假数字（实测「2025年3月哈萨克斯坦出口数量」曾算出 `501,181,485 米`）。
  改为只给金额并说明原因。

### 差异化引导

预测缺槽位时输出「已识别 / 还缺 / **该商品+伙伴在库中的贸易方式与注册地实际取值**」，
示例句随已识别槽位变化；商品名不在库中时直接给出规范名候选。

### 前端

路由标签按四类区分文案与颜色；`DATA_QUERY` 展示按月明细表；
**预测结果卡片只在有值时渲染**（此前无值也渲染，页面出现 `value=- / unit=-` 的空表格）。

## 五、检索规模的可见性（补充修复）

**问题**：来源列表只回 `topK=5` 条，用户看到 5 行就以为「系统一共只检索到 5 条」。
实际上向量库是对**全部 28,075 条**语料逐条算相似度、再取前 5 条。

**根因是两个概念被同一个数字绑住了**：

| 概念 | 含义 | 影响 |
|---|---|---|
| 上下文条数 `ai.vector.topK` | 真正拼进提示词的片段数 | 直接决定大模型耗时 |
| 候选条数 `ai.vector.candidate-topk` | 一次取回并展示的条数 | 决定用户能看到多少条 |

改前 `NewsRagService` 里还有一个硬编码的 `MAX_CONTEXT_DOCS = 5`，与 `topK` 重复定义；
一旦只把 `topK` 调大，就会出现「前端显示 10 条来源、模型其实只看到前 5 条」的静默不一致。

**改动**：

- 两个数字彻底分开：`candidate-topk`（默认 20）决定取回与展示条数，
  `topK`（默认 5）决定进提示词的条数。硬编码常量改为 `DEFAULT_CONTEXT_DOCS` 兜底。
- 响应新增 `corpusSize`（语料总条数）与 `contextDocs`（进上下文的条数）；
  每条来源新增 `usedInContext`，前端据此区分「已引用 / 仅相关」。
- 语料总条数取自向量库**内存计数**（`NewsVectorStore.size()`，新增默认方法，
  本地实现读 `rowCount`），不做 `COUNT(*)`，零额外 DB 往返。
- 前端默认只列已引用的那几条，并附一行说明「在全部 28,075 条语料中逐一比对相关度，
  取回 20 条候选，其中最高的 5 条已交给模型作答」，其余可一键展开。

**耗时对照**（同一问题连打 3 次，取稳态）：

| 候选条数 | 检索耗时 | 端到端耗时 |
|---|---|---|
| 5 | 163 / 258 / **86** ms | 5.32 / 1.74 / **1.35** s |
| 20 | 117 / 269 / **102** ms | 5.33 / 1.72 / **1.28** s |

结论：**无差异**。本地向量库是全量余弦扫描后维护 top-k，k 从 5 提到 20 的额外成本
可以忽略；端到端耗时由 DeepSeek 调用主导（约 1.2~1.5s），而提示词长度不变（仍 5 条）。

**验收**：`tools/qa_chat_accept.py` 新增 `check_rag_scale`，守住三条不变量 ——
`corpusSize` 如实填充、候选条数严格大于上下文条数（否则用户仍看不到检索规模）、
`usedInContext` 恰好在相关度最高的前 `contextDocs` 条上为真。11 项全部通过。

## 六、答案的 Markdown 渲染与等待反馈（补充修复）

**问题反馈**：回答里的 Markdown 没有被解析，页面上直接把 `**` 显示出来
（截图里「`**3.1992年上半年的进口结构（历史数据）：**`」一带即是）；
另外提交问题后、结果返回前，界面没有任何反馈。

**相关提交**：见本次提交（`feat(qa): 问答页渲染 Markdown 并补「正在深度思考」等待提示`）
**验收脚本**：`tools/qa_source_display_check.mjs`（A/B/C 三组，全部通过）

### 6.1 根因

模型（DeepSeek）返回的 `answer` 是 **Markdown 原文**，而模板里写的是
`<div class="bubble-text">{{ m.text }}</div>` —— 直接插值，Markdown 语法原样露出。
`/ai/chat` 又是**单次 POST、非流式**，RAG 一次问答端到端 1~2 秒，这段空窗期
页面毫无变化，用户会以为没点动。

### 6.2 改动

| 项 | 做法 |
|---|---|
| 解析 | 新增 `renderMd()`：`markdown-it` 解析 → `DOMPurify.sanitize()` → `v-html` |
| 安全① | markdown-it 设 `html: false`，模型输出里的原始 HTML 一律当**文本** |
| 安全② | DOMPurify 二次清洗，兜住 ① 覆盖不到的边角（如链接协议） |
| 外链 | 统一 `target="_blank"` + `rel="noopener noreferrer"` |
| 降级 | 解析或清洗抛错时退回转义后的纯文本 —— 宁可少渲染，不可白屏 |
| 排版 | 新增 `.md-body` 样式（标题 / 列表 / 表格 / 引用 / 代码块 / 分割线） |
| 等待 | `sending` 期间插入「正在深度思考」占位气泡（spinner + 三点动效） |
| 防连点 | `send()` 增加 `sending` 守卫，避免重复提交 |

**踩过的坑**：`v-html` 插入的是**子孙节点**，`<style scoped>` 的规则默认命中不了；
`.md-body` 下所有排版规则必须写成 `:deep(...)`，否则会出现「样式写了却没生效」。

### 6.3 安全实测

`html: false` 下，原始 HTML 输入被转义成**可读文本**，既不产生可执行节点，
也不是被静默吞掉（用户仍能看见原文）：

```
输入: <script>alert(1)</script> 与 <img src=x onerror=alert(2)>
输出: <p>&lt;script&gt;alert(1)&lt;/script&gt;</p>
      <p>&lt;img src=x onerror=alert(2)&gt;</p>
```

### 6.4 验收

`tools/qa_source_display_check.mjs` 从「只验来源展示」扩成三组：

| 组 | 覆盖 |
|---|---|
| A 来源展示 | 默认 5 条 / 其余进下拉 / 不丢不重 /「已引用 vs 仅相关」的划分 |
| B Markdown | `**…**` → `<strong>`、`- ` → `<ul>`、`###` → `<h3>`、表格 → `<table>`、反引号 → `<code>`、外链属性、原始 HTML 转义、空值不白屏 |
| C 等待占位 | 模板含「正在深度思考」且由 `sending` 驱动、正文已改 `v-html`、裸 `{{ m.text }}` 已移除 |

> B 组用的是**真实的 markdown-it**（经 `createRequire` 从前端工程的
> `package.json` 起算解析），不是打桩假装通过；只有 DOMPurify 因 Node 环境无 DOM
> 使用恒等桩，并在脚本输出里注明。

线上真实回答实测：原文 3 处 `**` 全部渲染为 `<strong>`，渲染后无 `**` 残留。

**产物**：`dist/js/app.52351635.js` 已上线（nginx 直接 root 到 `dist`，构建完即生效）。

## 七、「数据范围」路由与等待提示的可见性（2026-09-29 补充）

**问题反馈**：① 问「有什么国家的数据可以访问」，得到的是「我是中哈贸易智能助手，
可以帮你做三类事…」这段能力说明，答非所问；② 界面上看不到「正在深度思考」。

### 7.1 根因一：这段回答是写死的字符串，且从不提有哪些国家

用户看到的回答由 `AiChatController.buildCapabilityAnswer()` 输出，它是一条
**硬编码字符串**：把「历史数据覆盖 2015-01 ~ 2025-03」写在字面量里，且完全
没有贸易伙伴清单。这句话走了 `CHITCHAT` 路由（`debug.stage` 由规则/LLM 判定），
根本不经过模型生成 —— 这也是「LLM 没连上怎么还能回答」的答案：**那段话不需要 LLM**。

> 顺带确认 LLM 一直是通的：`backend-main.log` 里持续有
> `LLM 调用成功 https://api.deepseek.com/chat/completions HTTP 200` 与
> SiliconFlow embeddings 的成功记录。LLM 在这条链路上只被用来做**意图分类**。

### 7.2 改动

| 项 | 做法 |
|---|---|
| 新增 `SCOPE` 路由 | `IntentRouter` 加规则型判定（三个条件同时成立才算），**不进 LLM 四分类提示词**，避免扰动既有四类的分类行为 |
| 数据范围现算 | `TradeDataQueryService` 查伙伴清单、时间范围、记录数、商品数，产出 Markdown 表格 |
| 缓存策略 | 4 条聚合 SQL 冷算约 6.7s（`trade_out` 单表 191 万行，`COUNT(DISTINCT 商品编码)` 占 4.2s）→ 30 分钟 TTL + **启动后台预热** + **过期先返回旧值、后台刷新**，不把冷算甩到用户请求上 |
| CHITCHAT 兜底 | 能力说明里的数据范围改为动态；即使 SCOPE 规则漏判、问题落到 CHITCHAT，也不会答非所问 |
| 前端标签 | `SCOPE → 数据范围`（cyan），不再把内部路由名显示给用户 |

**判定条件**（`isScopeQuestion`）：需同时命中
① 询问词（哪些/什么/多少/范围/覆盖/支持/包含）、
② 对象词（数据/语料/资料/国家/地区/国别/贸易伙伴）、
③ 访问动词（访问/能查/可以查/获取/覆盖/包含/看得到/有）。
单看任一个都会大面积误伤：「哪些」几乎出现在所有检索式问句里，「数据」常出现在
正常查数据的句子里，「有」是最高频的字。

### 7.3 根因二：等待提示不是没加，是"看不见"

后端对闲聊类问题**命中规则、不调模型**，「你好」实测 **6.8ms** 返回 ——
占位气泡一闪而过，主观感受就是「没有这个提示」。真实问答（RAG 约 1.5~2.9s）
本来就能看见，所以问题只在秒回这一类。

改法：`THINKING_MIN_MS = 450`，即占位至少停留 450ms；**只补不足的部分**，
已经等够久的请求额外延迟为 0（不拖慢正常问答）。实测「立即返回」停留 451ms，
「已耗时 5000ms」额外延迟 0ms。

### 7.4 根因三（环境）：为什么"改了但页面没变"

- `index.html` 此前**没有任何 `Cache-Control`**，落到浏览器的「启发式缓存」
  （约为 `(now - Last-Modified)` 的 10%），行为不可预测。带内容哈希的 js/css
  设 7 天缓存是对的，但 `index.html` 一旦被缓存住，重新构建后的新前端就加载不到。
  已加精确匹配 `location = /index.html` 声明 `no-cache, no-store, must-revalidate`。
- **但该改动需要 root 执行 `sudo nginx -t && sudo systemctl reload nginx` 才生效**
  （nginx master 由 root 启动，当前账号无免密 sudo）。当前已写入 `/etc` 与
  `deploy/nginx/trade.conf` 两处并通过语法校验，**尚未 reload**。
- 另一条同样常见的原因：SPA 页面**不刷新**就一直是内存里的旧 JS。
  改了前端后请强制刷新一次（Ctrl/Cmd + Shift + R）。
